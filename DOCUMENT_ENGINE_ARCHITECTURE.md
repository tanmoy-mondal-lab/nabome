## 1. Document Foundation

### 1.1 What

The foundational philosophy, lifecycle, ownership, integrity, relationships, versioning readiness, and permanence standards that govern every document generated by the Nabome platform.

### 1.2 Why

- **Business integrity:** Every document is an official business record — legally binding, permanently traceable, and auditable.
- **Zero manual formatting:** Documents must be professional and print-ready without any manual intervention.
- **Compliance:** Indian tax laws (GST), consumer protection regulations, and audit requirements demand complete, immutable business records.
- **Trust:** Customers and shop owners must receive consistent, professional documents.
- **Scalability:** Document architecture must handle 0 to 1M+ documents without redesign.

### 1.3 Where

Every invoice, order summary, packing slip, return slip, refund receipt, settlement report, finance report, export report, audit report, customer statement, shop statement, and custom document across the Nabome platform.

### 1.4 Document Philosophy

| Principle | Description | Rationale |
|-----------|-------------|-----------|
| **Immutable after generation** | Once generated, business documents are never modified | Legal integrity, audit trail |
| **Zero manual formatting** | Every document is professional and print-ready by default | User experience, brand consistency |
| **Permanent Document ID** | Every document gets a unique, permanent identifier | Traceability, retrieval |
| **Reproducible** | Any document can be regenerated with identical content | Recovery, audit |
| **Official business record** | Every generated document is a legal business record | Compliance |
| **Independent from business modules** | Document Engine operates independently from orders, payments, finance | Maintainability, testability |
| **Append-only lifecycle** | Document versions create new records, never overwrite | Audit trail |
| **Always auditable** | Every document generation, download, and access is logged | Compliance |
| **CDN-first delivery** | Documents served via signed URLs through CDN | Performance, security |
| **Mobile-first viewing** | Documents are readable on mobile devices without zooming | 70%+ mobile traffic |

### 1.6 Document Ownership

| Aspect | Standard | Rationale |
|--------|----------|-----------|
| **Primary owner** | Exactly one parent entity per document | No ambiguity |
| **Ownership transfer** | Not supported — create new document, archive old | Simplicity |
| **Orphan prevention** | Documents deleted when parent is hard-deleted (except financial) | Data integrity |
| **Financial documents** | Never deleted, even after parent deletion | Compliance |
| **Lifecycle control** | Parent entity controls document visibility | Consistent behavior |

### 1.7 Document Integrity

| Aspect | Standard | Rationale |
|--------|----------|-----------|
| **Content snapshot** | Document captures exact data at generation time | Historical accuracy |
| **Immutability** | Generated PDFs are never modified | Legal integrity |
| **Checksum** | SHA-256 checksum computed on generation | Tamper detection |
| **Version tracking** | Each regeneration creates a new version | Audit trail |
| **Metadata lock** | Document metadata (type, parent, version) is immutable | Traceability |
| **Generation timestamp** | Exact UTC timestamp on every document | Temporal accuracy |

## 3. Document Generation

### 3.1 What

The complete workflow for creating, validating, rendering, generating, storing, downloading, printing, regenerating, and archiving documents.

### 3.2 Why

- **Automation:** Documents are generated automatically without manual intervention
- **Reliability:** Every generation step is validated and logged
- **Performance:** Generation is async and non-blocking
- **Recovery:** Failed generations can be retried
- **Auditability:** Every generation is logged with full context

### 3.3 Where

Document generation API, order lifecycle, payment lifecycle, settlement lifecycle, admin dashboard, customer account, shop owner dashboard.

### 3.4 Generation Flow

```
┌─────────────────────────────────────────────────────────────────┐
│                    DOCUMENT GENERATION FLOW                       │
│                                                                  │
│  1. TRIGGER                                                      │
│     → Business event (order confirmed, refund processed)         │
│     → On-demand request (admin, customer, shop owner)            │
│     → Scheduled job (periodic reports)                           │
│                                                                  │
│  2. VALIDATE DATA                                                │
│     → Verify all required data is present                        │
│     → Verify data is in correct format                           │
│     → Verify no data inconsistencies                             │
│     → If invalid → return error, do not generate                 │
│                                                                  │
│  3. SELECT TEMPLATE                                              │
│     → Look up document type → template mapping                   │
│     → Select template version                                    │
│     → Load template with brand configuration                     │
│                                                                  │
│  4. POPULATE TEMPLATE                                             │
│     → Map data to template dynamic fields                        │
│     → Apply formatting rules (currency, date, number)            │
│     → Apply business rules (GST calculation, tax breakdown)      │
│     → Validate populated template                                │
│                                                                  │
│  5. RENDER HTML                                                  │
│     → Convert template to HTML                                   │
│     → Apply print styles (A4, margins, page breaks)              │
│     → Apply brand styling (logo, colors, typography)             │
│     → Add QR codes, barcodes if configured                       │
│                                                                  │
│  6. GENERATE PDF                                                 │
│     → Convert HTML to PDF using headless browser                 │
│     → Apply PDF metadata (title, author, subject)                │
│     → Compute SHA-256 checksum                                   │
│     → Validate PDF structure                                     │
│                                                                  │
│  7. STORE                                                        │
│     → Upload PDF to R2                                           │
│     → Create Document record in database                         │
│     → Create Media record (polymorphic ownership)                │
│     → Cache signed URL in KV                                     │
│                                                                  │
│  8. NOTIFY                                                       │
│     → Notify requester (download link)                           │
│     → Attach to relevant entity (order, settlement)              │
│     → Log generation event                                       │
│                                                                  │
│  9. SERVE                                                        │
│     → Generate signed URL (1-hour expiry)                        │
│     → Return to requester                                        │
│     → Log access event                                           │
└─────────────────────────────────────────────────────────────────┘
```

### 10.6 Ownership-Based Access

```typescript
// Customer can access their own invoice
function canAccessInvoice(user: User, invoice: Document): boolean {
  if (user.role === 'admin') return true;
  if (user.role === 'customer') {
    return invoice.order.profileId === user.id;
  }
  if (user.role === 'shop_owner') {
    return invoice.order.items.some(
      item => item.variant.product.shopId === user.shopId
    );
  }
  return false;
}
```

## 15. Mandatory Rules for AI Agents

### 15.1 What

Rules that every AI agent must follow when working with the Nabome Document Engine.

### 15.2 Why

- **Consistency:** Every AI agent produces identical document patterns
- **Quality:** No AI-generated code violates the standards
- **Security:** Document security is never compromised
- **Compliance:** Legal requirements are always met

### 15.3 Mandatory Rules

| Rule | Standard | Rationale |
|------|----------|-----------|
| **Every document has a Document ID** | GDOC_ public ID + type-specific display ID | Traceability |
| **Never modify generated documents** | PDFs are immutable after generation | Legal integrity |
| **Always use signed URLs** | Never expose direct R2 URLs | Security |
| **Always check permissions** | Verify user can access document before serving | Authorization |
| **Always log document access** | Every download/access logged with actor + timestamp | Audit trail |
| **Never store documents in database** | Store PDF in R2, metadata in PostgreSQL | Performance, cost |
| **Always use async generation** | Never block HTTP request on PDF generation | Performance |
| **Always compute checksum** | SHA-256 on every generated PDF | Tamper detection |
| **Always use template system** | Never hardcode document layouts | Maintainability |
| **Never skip data validation** | Validate all data before document generation | Accuracy |
| **Always use year-scoped sequences** | Display IDs reset each year | Prevent long numbers |
| **Never delete financial documents** | 7-year retention minimum | Legal compliance |
| **Always integrate via events** | Document generation triggered by business events | Decoupling |
| **Never mix Document Engine with business logic** | Document Engine is independent | Maintainability |
| **Always register new document types** | Add to document type registry before implementation | Completeness |
| **Never assume template structure** | Read existing templates before creating new | Compatibility |
| **Always use R2 for storage** | Never use Cloudinary for documents | Cost optimization |
| **Always create Media record** | Every document has a tracking record | Integrity |
| **Never expose internal UUIDs** | Use public IDs in API responses | Security |
| **Always validate PDF output** | Verify PDF structure after generation | Quality |

### 15.5 Document Engine Service Interface

```typescript
interface DocumentEngine {
  generate(documentType: DocumentType, data: DocumentData, options?: GenerateOptions): Promise<DocumentResult>;
  download(documentId: string, userId: string): Promise<SignedUrl>;
  verify(documentId: string): Promise<VerificationResult>;
  regenerate(documentId: string, reason: string, userId: string): Promise<DocumentResult>;
  list(filters: DocumentFilters, pagination: PaginationParams): Promise<DocumentList>;
  search(query: string, filters: DocumentFilters): Promise<DocumentList>;
  getHistory(documentId: string): Promise<DocumentHistory>;
  bulkDownload(documentIds: string[], userId: string): Promise<BulkDownloadResult>;
}

interface GenerateOptions {
  templateId?: string;
  version?: 'latest' | 'specific';
  specificVersion?: number;
  reason?: string;
}

interface DocumentResult {
  documentId: string;
  displayId: string;
  version: number;
  r2Key: string;
  checksum: string;
  signedUrl: string;
  generatedAt: string;
}

interface VerificationResult {
  valid: boolean;
  documentId: string;
  checksum: string;
  verifiedAt: string;
  match: boolean;
}
```
